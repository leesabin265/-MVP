# MPG 최종 보고서

악성 패턴 차단 API 게이트웨이 — 기획서(2026-11-25)의 M1~M5 구현과 측정 결과.
측정일 2026-11-25, 개발 컨테이너(4 vCPU 호스트, gateway 컨테이너는 compose에서 2 vCPU·1 GB로 제한).

## 2. 구성

```
클라이언트 ─HTTPS 443─▶ gateway(TLS 종료, 2 워커) ─HTTP─▶ 백엔드        [gw-net: internal]
                          │ XADD ▲ SUBSCRIBE / SELECT(읽기 전용)
                          ▼      │
                        redis · postgres                                 [data-net: internal]
                          ▲      │
관리자 ─HTTPS 9443─▶ nginx(콘솔) ─▶ admin-api                             [mgmt-net: internal]
```

- 백엔드는 internal 네트워크에만 붙어 있어 게이트웨이를 거치지 않고는 닿을 수 없다.
- gateway와 admin-api는 서로 직접 호출하지 않는다. 연결 고리는 DB의 `policy_versions`(읽기 전용 계정)와 Redis뿐이다.
- PostgreSQL 계정 분리: `mpg_gateway` 는 `policy_versions` SELECT만, `mpg_admin` 은 `audit_log` 에 INSERT·SELECT만(UPDATE·DELETE는 REVOKE + 트리거로 이중 차단). 테이블 소유자는 superuser다.
- Redis ACL: `mpg-gateway` 는 `gateway.events` XADD, 자기 상태 키 SET, `policy.updated` SUBSCRIBE만 가능. default 사용자는 끈다.

## 3. 요청 하나의 경로

1. **크기·형식**: CL+TE 동시 사용·중복 Content-Length → 400, 1 MB 초과 → 413, 깨진 JSON·멀티파트·깊이 32 초과 → 400.
2. **필드 추출** (`gateway/extract.py`): 경로, 쿼리(값은 **전송된 그대로**, 이름도 검사), User-Agent·Referer, 쿠키 각각, form·JSON(값과 키)·multipart 텍스트 필드·파일명.
   Content-Type이 그 밖이어도 본문이 `{`·`[` 로 시작하면 JSON으로 파싱해 보고, 아니면 본문 전체를 한 필드로 검사한다(Content-Type 위장 대응).
3. **정규화** (`detection/normalizer.py`): URL 디코딩 최대 3회(쿼리·폼은 1회차만 `+`→공백, IIS `%uXXXX` 포함) → HTML 엔티티 → JS 이스케이프(`\xNN`·`\uNNNN` 4개 이상 연속일 때) → NFKC → 제어문자 제거 → 주석 제거(MySQL `/*!50000 */` 은 내용 보존) → 소문자 → 공백 1칸.
   각 단계에서 우회 신호(다중 인코딩, 3회 후에도 남은 인코딩, 전각 특수문자, 키워드 사이 주석, 대소문자 혼용, 제어문자, 중복 파라미터)를 뽑는다.
4. **프리필터**: 룰 키워드로 만든 Aho-Corasick 오토마톤으로 후보 룰만 고른다. 정상 한국어 문장은 대개 후보 0개.
5. **정밀 분석**: RE2 정규식 41개 + 토큰 분석기 1개(SQLI-010).
6. **점수 판정**: 필드별 점수 = 매칭 룰 가중치 합 + 신호 룰 가중치 − 예외. 요청 점수 = 필드 최댓값.
   BLOCK 모드 룰 합 ≥ 6 → 403, 전체 합 ≥ 6 → 전달 + 기록, 그 외 전달.
7. **이벤트**: DETECT_ONLY·BLOCK만 워커 메모리 deque에 넣고(await 없음) 백그라운드 태스크가 묶어서 XADD. admin-api 소비 그룹이 DB 커밋 후 XACK.

## 4. 데이터셋과 측정의 정직성

| 단계 | 공격 | 정상 | 탐지율 | 오탐률 |
|---|---:|---:|---:|---:|
| M1 1차본, 튜닝 전 | 569 | 320 | 93.50% | 1.88% |
| M1 1차본, 튜닝 후 | 569 | 320 | 100% | 0% |
| M1 직후, 튜닝에 안 쓴 기술 Q&A 40문장 | — | 40 | — | 차단 20% → 수정 후 10% |
| **M4 확장 셋, 튜닝 전** | 2,083 | 1,000 | **94.05%** | **1.70%** |
| M4 확장 셋, 튜닝 후(최종) | 2,081 | 1,000 | 100% | 0% |
| 최종 정책으로 어려운 기술 Q&A 40문장 | — | 40 | — | **차단 10% (4건)** |

- 확장 셋에서 튜닝 전 미탐은 **기본 페이로드 10여 개**에 몰려 있었다(변형별로 8~15개씩). 개별 페이로드가 아니라 **기법 단위**로 룰을 추가했다:
  괄호 서브쿼리(SQLI-017), CASE WHEN(SQLI-018), `IS NULL` 비교, 따옴표 없는 문맥의 문자열 tautology(SQLI-011 확장), 스킴 안 탭·개행 허용 `j\s*a\s*v\s*a…`(XSS-003),
  JS 문자열 탈출 `'-alert(1)-'`(XSS-015), `link rel=import`·`meta refresh`(XSS-013 확장), data URI 분리(XSS-007/016).
- 확장 셋의 튜닝 전 오탐 17건은 전부 `It's 'fine' -- don't worry` 였다. 토큰 분석기가 **닫는** 따옴표 뒤의 `--` 를 탈출로 본 것이 원인이라, 값 안에서 같은 종류 따옴표의 홀수 번째(여는 쪽)만 후보로 보도록 바꿨다.
- 남은 4건(`<script> 태그를…`, `<button onclick="save()">`, `Union SELECT 공격이…`, `A and 1=1`)은 문자열만으로 실제 페이로드와 구분할 수 없다. 이것이 시나리오 B가 다루는 경우이고, 경로·파라미터 단위 예외로 처리한다.
- 생성기가 만든 **무효 페이로드도 걸러냈다**: `&#x3cbody`(브라우저도 `&#x3cb` 까지 읽어 공격 불성립), 쿼리의 리터럴 `+`(공백이 됨), 폼·쿼리 값의 인코딩 안 된 `&`·`#`(값이 잘림).
  마지막 것은 실제 HTTP 재생(`tools/replay.py`)에서 오프라인 엔진과 54건 불일치로 드러났고, 백엔드 응답으로 공격이 전달되지 않음을 확인한 뒤 생성기를 고쳤다. 수정 후 **3,121건 전부 게이트웨이 판정 = 오프라인 엔진 판정**.

| 임계값 | 탐지율 | 차단율 | 오탐률(정상 1,000) | 차단 오탐(어려운 40) |
|---:|---:|---:|---:|---:|
| 4 | 100.00% | 99.95% | 0.20% | 27.5% |
| 5 | 100.00% | 99.71% | 0.00% | 12.5% |
| **6** | **100.00%** | **99.47%** | **0.00%** | **10.0%** |
| 7 | 86.83% | 85.58% | 0.00% | 5.0% |
| 8 | 82.56% | 80.97% | 0.00% | 0.0% |

6이 꺾이는 지점이다. 7로 올리면 탐지율이 13%p 떨어진다. 기술 Q&A 게시판처럼 공격 문법을 정상적으로 쓰는 경로의 오탐은 전역 임계값으로는 줄일 수 없으므로,
경로별 임계값(쟁점 #1 ②안)을 구현했다(아래).

### 경로별 차단 임계값 (쟁점 #1 ②안, 구현)

경로(정확히 일치 또는 접두사)·파라미터 단위로 **차단 임계값만** 바꾼다. 탐지 임계값은 `min(전역, 경로)` 라서,
올리면 그 사이 점수의 요청은 조용히 통과하지 않고 DETECT_ONLY로 기록되고, 내리면(로그인 경로 등) 더 엄격해진다.
여러 설정이 겹치면 정확한 경로 > 접두사, 파라미터 지정 > 경로 전체, 긴 경로 > 짧은 경로 순으로 하나만 적용한다.

`/api/qna/posts` · `content` 의 차단 임계값을 바꾸며 측정(전역 6 유지, 이 경로 공격 278건):

| 차단 임계값 | 이 경로 공격 탐지율 | 이 경로 공격 차단율 | 전체 차단율 | 어려운 40 차단 | 어려운 40 기록만 |
|---:|---:|---:|---:|---:|---:|
| 6 (기본) | 100.00% | 98.20% | 99.52% | 4/40 | 2/40 |
| 7 | 100.00% | 96.40% | 99.28% | 2/40 | 4/40 |
| **8** | **100.00%** | **92.45%** | **98.75%** | **0/40** | 6/40 |
| 9 | 100.00% | 87.05% | 98.03% | 0/40 | 6/40 |
| 10 | 100.00% | 78.06% | 96.83% | 0/40 | 6/40 |

전역 임계값을 8로 올리면 전체 탐지율이 82.65%로 떨어지는 것과 달리, 게시판 본문에만 8을 주면 탐지율 100%를 유지하면서 어려운 셋 차단 오탐이 0이 된다.
대가는 이 경로를 노리는 공격의 7.55%가 차단 대신 기록만 된다는 점이다(백엔드의 출력 이스케이프에 의존). 그래서 기본값으로 넣지 않고 운영자가 고르게 했다.

- 안전장치: ADMIN만 추가·삭제, 사유 필수(감사 기록), 범위 3 ~ 전역+4, 와일드카드 금지(접두사는 명시적 플래그), `/` 접두사 금지(전역값을 바꾸라는 뜻),
  발행 때 회귀 게이트를 그대로 거치며 차단율 하락은 경고로 표시(탐지율은 떨어지지 않으므로 거부 사유가 아니다).
- 저장: `path_thresholds` 테이블(기획서 8개 + 1). 기존 배포는 `docker compose exec -T postgres psql -U postgres -d mpg < src/mpg/admin/schema.sql` 로 업그레이드(멱등).

## 5. 부하·장애 측정 상세

**k6** (`loadtest/load.js`, 요청 구성: 상품 조회 70%, 검색 20%, 1 KB 게시글 작성 10%)

| 경로 | 요청 | 실패 | 평균 | p50 | p95 | p99 | 최대 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 백엔드 직접 (HTTP) | 54,001 | 0 | 0.57 ms | 0.54 ms | 0.86 ms | 1.10 ms | 9.0 ms |
| 게이트웨이 (HTTPS) | 180,001 | 0 | 2.34 ms | 2.08 ms | 3.58 ms | 6.75 ms | 91.9 ms |

- 게이트웨이 경로는 TLS 암호화 비용까지 포함하므로 보수적인 수치다. 게이트웨이 내부 히스토그램으로는 **검사 p99 ≤ 0.5 ms**, 앱 안 추가 지연 p95 ≤ 1 ms, p99 ≤ 3 ms였다.
  즉 추가 지연의 대부분은 탐지가 아니라 TLS·HTTP 파싱·프록시 홉이다.
- k6와 게이트웨이가 같은 호스트에서 CPU를 나눠 쓴 상태라, 실제 2 vCPU 전용 호스트에서는 조금 더 나을 것이다. 최대 91.9 ms는 측정 5분 시점의 정책 발행과 겹친 순간으로 보이나 원인은 특정하지 못했다.
- 기획서 쟁점 #4(“Python으로 300 RPS·p95 5 ms 가능한가”)는 **Uvicorn 워커 2개로 충족**했다. C 확장은 필요 없었다.

## 6. 개발 중 찾아 고친 결함

| 결함 | 영향 | 수정 |
|---|---|---|
| 시나리오 A가 SQLI-001과 SQLI-011에 중복 집계(16점) | 같은 증거를 두 번 세어 가중치 설계가 무의미 | SQLI-011을 따옴표 없는 문맥으로 한정 |
| 정규화기가 1 MB 입력에서 1.6초 | 목표의 30배 | google-re2 Python 바인딩의 `sub`가 매치마다 UTF-8↔str 오프셋을 변환. 고정 치환은 `str` 연산·선형 스캔으로 교체 |
| 회귀 거부 감사 기록이 사라짐 | 422 응답과 함께 트랜잭션이 롤백되어 `policy.publish_rejected` 미기록 | 거부 기록을 별도 트랜잭션으로 커밋 |
| `mpgctl create-admin --if-missing` 교착 | 커넥션을 쥔 채 `pool.close()` → init 컨테이너 무한 대기 | acquire 블록 밖에서 close |
| DB 복구 후에도 "리로드 실패" 알림 지속 | 같은 버전이면 오류를 지우기 전에 반환 | 조회 성공 시 오류 초기화 |
| 롤백 후 근거 없는 "미발행 변경" | 대상 버전에 없던 비활성 룰을 "추가"로 셈 | 비활성 + 발행본에 없음 → 변경 아님 |
| nginx HSTS 누락 | location의 `add_header` 가 server 블록 헤더 상속을 끊음 | location마다 지정 |

## 7. 보안 설계 요약

- 공격자에게는 `{"error":"blocked","request_id":…}` 만 준다(룰 ID·점수 비공개).
- 운영자 룰은 RE2만 허용(등록 시 컴파일 검사, 역참조·lookaround 거부). RE2는 Thompson NFA/DFA 기반이라 입력 길이에 선형이다(Russ Cox, *Regular Expression Matching Can Be Simple And Fast*, 2007).
- 예외는 룰 1개·경로·파라미터·만료일(≤ 180일) 필수, 와일드카드 금지(앱 검증 + DB CHECK 제약 이중), 회귀 게이트 통과 후에만 반영.
- 관리자: Argon2id, 5회 실패 15분 잠금 + IP당 10분 20회 제한, 세션은 Redis에 SHA-256 키로 저장(덤프로 세션 탈취 불가), 유휴 30분,
  쿠키 `HttpOnly; Secure; SameSite=Strict; Path=/admin/api`, 상태 변경 요청은 `X-CSRF-Token`, 역할 검사는 매 요청 DB에서 다시 확인.
- 콘솔은 모든 로그를 텍스트 노드로 렌더링(React 자동 이스케이프, `dangerouslySetInnerHTML` 미사용) + `script-src 'self'` CSP — 저장된 XSS 페이로드가 콘솔에서 실행되지 않는다.
- 로그에 남기지 않는 것: 요청 본문 원문, 쿠키 값, `password`·`token`·`secret` 류 파라미터 값. 샘플은 256자, 이메일·전화번호·긴 토큰 마스킹.
- 컨테이너: 비루트(uid 10001), 읽기 전용 루트 FS, `cap_drop: ALL`, `no-new-privileges`, 비밀값은 Docker secrets 파일.

## 8. 한계와 남은 일 (2차 반영)

- **일반화 성능이 낮다(가장 큰 문제)**: 외부 데이터(OWASP CRS PL1)에서 SQLi 25%, XSS 34%, RCE 8%, LFI 21%만 잡았다(10장).
  직접 만든 셋의 100%는 그 셋에 맞춘 결과다. CRS의 일부를 튜닝용으로 떼고 나머지로 다시 재는 2차 튜닝이 필요하다(아직 하지 않음 — CRS를 측정 전용으로 남겼다).
- **운영 트래픽 재측정**: 도구(`tools/traffic_eval.py`)만 만들었다. 실제 운영 로그·캡처가 없어 수치는 아직 없다.
- **게시판 문맥 오탐**: 임계값 8 + XSS-004 차단 설정으로 이 경로 공격 중 기록만 되는 비율을 7.55% → 3.96%로 줄였지만 0은 아니다(나머지 11건은 정상 글과 문자열로 구분되지 않는다).
- **응답 검사 범위**: 텍스트 응답의 앞 256 KB만, gzip·deflate만 푼다(br은 검사하지 않고 통과). CRS 응답 유출 사례 탐지율은 낮다(10장).
- **업로드 검사**: 매직 넘버·확장자·내장 코드만 본다. 압축 파일 안·Office 매크로·이미지 재인코딩 검사는 없다. 회귀 데이터셋에는 업로드 사례가 없다(단위·e2e 테스트로만 확인).
- **경로 조작 탐지**: 게이트웨이는 요청 문자열만 본다. 실제로 열리는 파일 경로는 백엔드가 정하므로 백엔드의 경로 정규화·허용 목록이 여전히 필요하다.
- **MVP JS 엔진과의 대조**: JS 원본이 없어 수행하지 못했다. 기획서의 시나리오 점수(A=10, B=11)를 정확히 재현하는 것으로 대신했다.
- 개발 환경 Python은 3.13(기획서 3.14.9), 데모 서버 실배포(공인 도메인 + Let's Encrypt)는 하지 않았다.
- 1 MB ReDoS형 입력 3종(`' or`·`<a onx`·`union` 반복)은 이 개발 PC(4코어)에서 100~220 ms로 테스트 기준(100 ms)을 넘는다. 1차 측정 환경에서는 15~40 ms였다. 하드웨어 차이로 보이지만 원인은 확인하지 못했다.

## 10. 2차 개선 (2026-11-27)

8장의 한계 항목을 구현·측정했다. 룰 51개 → 74개(SQLI 18 · XSS 16 · SCR 9 · CMD 6 · PATH 5 · FILE 5 · RESP 7 · ENC 8).

### 10.1 경로별 룰 모드(경로별 룰 그룹)

경로(정확히 일치·접두사)·파라미터 단위로 **룰 하나의 모드**를 바꾼다. DETECT로 낮추면 그 룰은 이 경로에서 차단 점수에서 빠지고 기록만 되며,
BLOCK으로 올리면 전역에서는 탐지만 하는 룰이 이 경로에서는 차단 점수에 들어간다. 경로별 임계값과 같은 우선순위(가장 구체적인 하나)·안전장치
(ADMIN 전용, 사유 필수, 와일드카드·`/` 접두사 금지, 회귀 게이트)를 쓴다. 저장은 `path_rule_overrides` 테이블, 콘솔은 '경로별 설정' 화면.
전역 모드와 같아 바뀌는 게 없는 설정은 등록할 때만 거부한다(스냅샷 읽기에서 거부하면, 나중에 룰의 전역 모드를 바꿨을 때 게이트웨이 리로드가 깨진다).

**게시판 임계값 8의 대가 줄이기.** 먼저 "오탐을 내는 룰만 게시판에서 DETECT로" 를 측정했는데, 게시판 XSS 공격 상당수가 바로 그 룰(XSS-001·XSS-002)
하나로만 잡혀 오히려 나빠졌다(XSS-001·002를 DETECT로 하면 차단 278건 중 181건). 임계값과 룰 모드를 조합한 전체 경우에서 '어려운 40 차단 0'을 지키는
최선은 임계값 8 단독이었다. 반대로 **강화**를 보니, 임계값 8에서 기록만 되던 21건 중 10건이 `<embed>`·`<base href>`·`<link rel=import>` 로
XSS-004(전역 DETECT 모드)가 차단 점수에 안 들어가서였다. 게시판 본문에서만 XSS-004를 BLOCK으로 올렸다:

| 게시판 본문 설정 | 이 경로 공격 278건 중 차단 안 됨 | 탐지율 | 어려운 40 차단 | 정상 셋 차단 오탐 |
|---|---:|---:|---:|---:|
| 임계값 6 (설정 없음) | 5 (1.80%) | 100% | 4/40 | 0 |
| 임계값 8 (1차) | 21 (7.55%) | 100% | 0/40 | 0 |
| **임계값 8 + XSS-004 차단 (2차 기본값)** | **11 (3.96%)** | 100% | **0/40** | 0 |

남은 11건(`<script src=//…>`, `javascript:alert(1)`, `<a href="data:text/html;…">` 등)은 어려운 셋의 정상 글과 같은 룰 하나로만 걸려 문자열로는 가를 수 없다.
주의: 이 결정은 게시판 공격 셋을 보고 내렸다(공격 셋은 원래 튜닝용). 어려운 40은 차단 0 확인에만 썼다.

### 10.2 퍼센트 이스케이프 폭주

- **정규화 지름길(판정 불변)**: 유효한 `%XX`·`%uXXXX` 가 하나도 없으면 `unquote` 결과는 입력과 같으므로 부르지 않는다. 1 MB의 `%` 만 있는 입력이 0.3~0.6 s → 수 ms.
  옛 반복 규칙과 결과가 같은지 무작위 입력 2만 개로 대조하는 테스트를 넣었다. 디코더 자체는 바꾸지 않았다(백엔드와 다르게 디코딩하면 우회 경로).
- **요청당 '%' 상한(파서 제한)**: 기본 10만 개(URL 인코딩된 한글 약 3만 3천 자, 폼 본문 약 300 KB). 넘으면 400. 점수가 아니라 파서 제한이라 경로별 설정으로 풀 수 없다.
  `GATEWAY_MAX_PCT_ESCAPES` 로 조정. 밀도 상한 대신 개수 상한을 고른 이유: 1 MB 한글 폼은 이스케이프 밀도가 100%에 가까워 밀도로는 정상과 공격을 가를 수 없다.
- 결과(리눅스 컨테이너): 1 MB `%25` 반복 257 ms → 113 ms, 운영에서는 상한에 걸려 검사 전에 400.

### 10.3 명령어 삽입(CMD)·경로 조작(PATH)

- CMD 6개: 셸 구분자 뒤 명령, `$(…)`·백틱 명령 치환, 역방향 셸·`curl|sh`, `$IFS`, 구분자 뒤 Windows 명령, 개행 뒤 명령(정규화가 공백으로 합치기 전에 `newline_command` 신호로 남긴다).
- PATH 5개: 2단계 이상 상위 탈출(`../`, `..\`, `....//`, 오버롱 UTF-8 `%c0%af`), 민감 파일, 값 전체가 시스템 디렉터리·드라이브 경로, 스트림 래퍼(`php://` 등), `file://`.
- 설계: 경로 문자열·명령어 단어 하나로는 차단 기준(6)에 닿지 않는다(`../../components`, `ls -al`, `$(document)` 는 통과). 셸 문법이 성립하거나 탈출 + 민감 파일이 함께일 때만 차단.
- 데이터셋: 공격 205건(CMD 133 · PATH 72) · 정상 68건을 생성기에 **뒤에 붙여** 기존 2,081·1,000건은 바이트 단위로 그대로다. **튜닝 전 결과 그대로**: 새 공격 205건 전부 차단, 새 정상 68건 오탐 0.
  다만 기존 정상 셋 중 게시판 글 4건(여러 줄 코드의 줄 머리 `curl …`)이 CMD-006으로 '기록만' 된다 — 게시판 임계값 8 때문에 차단은 안 된다. 그 4건에 맞춰 룰을 고치지 않았다.

### 10.4 업로드 파일 내용 검사

multipart 파일 파트마다 `src/mpg/gateway/uploads.py` 가 판정한다. 기준은 파일 이름·Content-Type이 아니라 **실제 바이트(매직 넘버)**.
텍스트 파일(UTF-8, NUL 없음)은 내용을 `이름#content` 필드로 넘겨 XSS·SCR·CMD 룰이 그대로 보고, 파일 자체에 대한 사실은 신호로 FILE 룰이 점수를 준다:
서버 실행 확장자(FILE-001), 이중 확장자 `shell.php.jpg`(FILE-002), 이미지·문서라 선언했지만 HTML·스크립트·실행 파일(FILE-003),
이미지·PDF 안에 `<?php`·`<script`(폴리글롯 웹셸, FILE-004), ELF·PE·Mach-O(FILE-005, 기본은 기록만).

**함께 고친 기존 결함**: 한글 파일 이름(`사진.jpg`)이 든 multipart를 `email` 헤더 파서가 `Header` 객체로 돌려줘 예외가 났고, 검사 예외는 Fail-Closed라
**한글 이름 파일 업로드가 전부 403**이었다. 파트 헤더를 UTF-8로 직접 읽도록 바꿨다.

### 10.5 응답 검사(정보 유출)

백엔드 응답 중 텍스트(JSON·HTML·text, `+json`·`+xml`)의 앞 256 KB를 담아 RESP 룰로 검사한 뒤 그대로 흘려보낸다(초과분은 스트리밍).
gzip·deflate는 4 MB까지 풀어 본다. DB 오류(RESP-001)·스택 트레이스(RESP-002)·`/etc/passwd` 내용(RESP-003)·개인 키(RESP-004)·클라우드 키(RESP-005)·디렉터리 목록(RESP-006).
DB 오류·스택 트레이스는 **5xx 응답일 때만** 차단 점수에 닿는다(+RESP-007 신호): 게시판 목록이 "SQL syntax 오류가 나요" 같은 글을 담아 200으로 나가도 막지 않고 기록만 한다.
차단하면 응답을 `502 {"error":"response_blocked"}` 로 바꾸고, 이벤트 샘플에는 유출된 원문 대신 `[response redacted]` 만 남긴다.
요청 판정과 응답 판정은 이벤트 한 건으로 합친다(`security_events` 는 요청 ID당 한 건). 응답 검사 중 예외는 응답을 막지 않는다(Fail-Open, 지표로 셈) — 요청 검사와 반대인 이유는
검사기 결함 하나로 모든 응답이 끊기는 것을 피하려는 것이다. 경로·`$response` 파라미터로 임계값·룰 모드·예외를 걸 수 있다.

### 10.6 게이트웨이 여러 대 + 내부망 TLS

```
클라이언트 ─TLS 443─▶ edge-lb(HAProxy) ─TLS(사설 CA 검증)─▶ gateway ×N ─TLS─▶ backend
                                                          │  TLS(verify-full) · TLS
                                                          ▼
                                                   postgres · redis ◀─TLS── admin-api ◀─TLS── nginx(콘솔)
```

- **여러 대**: `GATEWAY_REPLICAS`(기본 2). HAProxy가 Docker DNS로 복제본을 찾아 라운드로빈하고 `/__mpg/health` 로 3초마다 점검한다.
  클라이언트가 보낸 `X-Forwarded-For` 는 LB에서 버리고 실제 주소만 넣으며, 게이트웨이는 LB 주소(172.28.50.10)만 신뢰한다.
  `/__mpg/*` 접근 판단도 LB 뒤의 실제 클라이언트 주소로 하도록 바꿨다(그대로 두면 LB를 거친 모든 요청이 '내부'로 보인다).
  정책 캐시 파일을 여러 대가 같은 볼륨에 쓰므로 임시 파일 이름을 프로세스마다 다르게 했다. 대시보드·알림은 이미 인스턴스별이었다.
- **확인**: 게이트웨이 1대를 멈춘 채 30건 요청 → 30건 모두 200. e2e의 정책 반영 대기는 '연속 (대수×2)번 새 버전'을 봐야 통과하게 바꿨다(한 대만 보고 넘어가지 않게).
- **내부망 TLS**: `gen-secrets.sh` 가 사설 CA와 서비스별 인증서(SAN = compose 서비스 이름)를 만든다. CA 키는 어느 컨테이너에도 넣지 않는다.
  PostgreSQL은 `hostnossl … reject`(평문 접속 거부, 확인함), 앱은 `sslmode=verify-full`. Redis는 평문 포트를 닫고(`--port 0`) TLS만, 클라이언트는 인증서·호스트 이름 검증.
  backend·admin-api는 HTTPS만 열고 게이트웨이·nginx가 사설 CA로 검증한다(평문 HTTP·CA 없는 HTTPS 둘 다 실패 확인).
- 함께 고친 것: Windows Git Bash에서 `openssl rand` 출력의 `\r` 이 비밀번호에 섞일 수 있었다(`tr` 가 `\n` 만 지움). Redis ACL 파서가 `\r` 을 공백으로 봐서 우연히 동작하고 있었다.

### 10.7 외부 데이터로 다시 재기 — OWASP CRS 회귀 테스트

`tools/crs_eval.py` 가 CRS 회귀 테스트(Apache-2.0)의 요청을 게이트웨이와 같은 코드(`build_inspection` → 파이프라인)로 판정한다. **MPG 룰은 이 데이터로 튜닝하지 않았다.**
CRS 룰마다 paranoia level(PL)이 있다. CRS 기본값은 PL1이고 PL2~4는 CRS도 오탐을 감수하는 약한 신호다. 아래는 공격(expect_ids) 사례만:

| 분류 | PL1 사례 | PL1 차단 | PL1 탐지(차단+기록) | 전 PL 사례 |
|---|---:|---:|---:|---:|
| SQLi (942) | 324 | 25.0% | 25.0% | 872 |
| XSS (941) | 188 | 29.3% | 34.0% | 209 |
| RCE (932) | 452 | 8.0% | 8.0% | 791 |
| LFI (930) | 57 | 21.1% | 21.1% | 67 |
| RFI (931) | 14 | 0.0% | 0.0% | 36 |
| PHP (933) | 275 | 11.3% | 11.3% | 326 |
| Java (944) | 604 | 11.1% | 11.1% | 1,142 |

- **읽는 법**: 직접 만든 셋의 탐지율 100%는 일반 성능이 아니다. 외부 PL1 공격의 대부분을 놓친다.
- **왜**: (1) 위치 — 쿼리 문자열(MPG가 전부 검사하는 곳)에 든 PL1 공격도 92%를 놓쳤으니 범위 탓만은 아니다. 다만 임의 헤더(141건 중 140건 놓침)·XML 본문·쿠키 이름 등
  MPG가 보지 않는 위치도 많다. (2) 기준 — CRS PL1은 `sleep(20)` 하나, PowerShell 명령 이름 하나도 공격으로 센다. MPG는 오탐을 줄이려 단일 약한 신호로는 막지 않게 설계했다.
  (3) 진짜 빈틈 — `cat /etc/pa[s]swd`(셸 글롭), `’ OR 1=1`(U+2019 따옴표), `onxxx= =` 형태, Java 클래스·역직렬화 페이로드, 다양한 RCE 우회 등 MPG 셋에 없던 기법.
- **참고(오탐 쪽)**: '그 룰이 걸리면 안 되는' CRS 사례(no_expect_ids)에서 차단 0~5.9%. 이 사례에는 다른 룰이 잡아야 할 공격도 섞여 있어 오탐률로 읽으면 안 된다.
- **응답 유출 사례(950~956)**: DB 오류 25%, PHP 8%, 나머지 0%. CRS는 각 DB·언어별 오류 문구를 수백 개 가진다.
- 다음 단계(하지 않음): CRS 사례를 튜닝용·측정용으로 나눠 룰을 보강하고 측정용으로만 다시 잰다. 지금 결과는 CRS를 전부 측정용으로 남긴 상태의 기준선이다.

### 10.8 운영 트래픽 재측정 도구

`tools/traffic_eval.py` — nginx/Apache combined 로그(본문 없음) 또는 JSONL 캡처를 같은 판정 코드로 돌려 판정 분포·많이 걸린 룰·경로를 내고,
차단·기록된 요청을 마스킹해 `--review` 파일로 뽑는다. 사람이 `label`(attack/normal)을 달아 다시 넣으면 그 표본으로 탐지율·오탐률을 계산한다.
**운영 트래픽이 없어 수치는 아직 없다.** 운영 로그를 넣으면 바로 잴 수 있다.
