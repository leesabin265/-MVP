# MPG 최종 보고서

악성 패턴 차단 API 게이트웨이 — 기획서(2026-11-25)의 M1~M5 구현과 측정 결과.
측정일 2026-11-25, 개발 컨테이너(4 vCPU 호스트, gateway 컨테이너는 compose에서 2 vCPU·1 GB로 제한).

## 1. 목표 대비 결과

| 기획서 지표 | 목표 | 결과 | 근거 |
|---|---|---|---|
| 추가 지연 | p95 ≤ 5 ms, p99 ≤ 15 ms | **p95 +2.72 ms, p99 +5.65 ms** | k6, 같은 요청을 직접/경유로 300 RPS (`docs/loadtest/k6-output.txt`) |
| 처리 규모 | 300 RPS 10분, 오류율 < 0.1% | **180,001건, 실패 0건** | 같은 k6 실행(게이트웨이 구간 10분) |
| 최악 입력 검사 시간 | 1 MB에서 50 ms 이하, 선형 | ReDoS형 입력 15~40 ms, 선형 확인 | `tests/test_performance.py` |
| 탐지율 | ≥ 95% (공격 2,000건 이상) | **100%** (2,081건), 차단 99.52% | `datasets/regress-report.json` |
| 오탐률 | ≤ 1% (정상 1,000건 이상) | **0.00%** (1,000건) | 같은 리포트 |
| 가용성 | admin-api·DB 중단 중 차단 100% 유지 | **판정 일치 300/300**, 5xx 0 | `docs/outage-drill.json` |
| 핫 리로드 | 발행 후 3초 이내, 실패 0 | **발행 응답 시점에 두 워커 모두 반영**(첫 확인 17 ms), 부하 중 실패 0 | `docs/loadtest/reload-probe.json` |
| 이벤트 유실 | 0건 | **0건** (기대 500건 전부 적재, Redis 중단 포함) | `docs/outage-drill.json` |

주의: 탐지율·오탐률은 **직접 만든 데이터셋** 기준이다. 튜닝 전 수치와 튜닝에 쓰지 않은 셋의 결과를 4장에 따로 적었다.

## 2. 구성

```
클라이언트 ─HTTPS 443─▶ gateway(TLS 종료, 2 워커) ─HTTP─▶ 백엔드        [gw-net: internal]
                          │ XADD ▲ SUBSCRIBE / SELECT(읽기 전용)
                          ▼      │
                        redis · postgres                                 [data-net: internal]
                          ▲      │
관리자 ─HTTPS 9443─▶ nginx(콘솔) ─▶ admin-api                             [mgmt-net: internal]
```

- 백엔드는 internal 네트워크에만 붙어 있어 게이트웨이를 거치지 않고는 닿을 수 없다.
- gateway와 admin-api는 서로 직접 호출하지 않는다. 연결 고리는 DB의 `policy_versions`(읽기 전용 계정)와 Redis뿐이다.
- PostgreSQL 계정 분리: `mpg_gateway` 는 `policy_versions` SELECT만, `mpg_admin` 은 `audit_log` 에 INSERT·SELECT만(UPDATE·DELETE는 REVOKE + 트리거로 이중 차단). 테이블 소유자는 superuser다.
- Redis ACL: `mpg-gateway` 는 `gateway.events` XADD, 자기 상태 키 SET, `policy.updated` SUBSCRIBE만 가능. default 사용자는 끈다.

## 3. 요청 하나의 경로

1. **크기·형식**: CL+TE 동시 사용·중복 Content-Length → 400, 1 MB 초과 → 413, 깨진 JSON·멀티파트·깊이 32 초과 → 400.
2. **필드 추출** (`gateway/extract.py`): 경로, 쿼리(값은 **전송된 그대로**, 이름도 검사), User-Agent·Referer, 쿠키 각각, form·JSON(값과 키)·multipart 텍스트 필드·파일명.
   Content-Type이 그 밖이어도 본문이 `{`·`[` 로 시작하면 JSON으로 파싱해 보고, 아니면 본문 전체를 한 필드로 검사한다(Content-Type 위장 대응).
3. **정규화** (`detection/normalizer.py`): URL 디코딩 최대 3회(쿼리·폼은 1회차만 `+`→공백, IIS `%uXXXX` 포함) → HTML 엔티티 → JS 이스케이프(`\xNN`·`\uNNNN` 4개 이상 연속일 때) → NFKC → 제어문자 제거 → 주석 제거(MySQL `/*!50000 */` 은 내용 보존) → 소문자 → 공백 1칸.
   각 단계에서 우회 신호(다중 인코딩, 3회 후에도 남은 인코딩, 전각 특수문자, 키워드 사이 주석, 대소문자 혼용, 제어문자, 중복 파라미터)를 뽑는다.
4. **프리필터**: 룰 키워드로 만든 Aho-Corasick 오토마톤으로 후보 룰만 고른다. 정상 한국어 문장은 대개 후보 0개.
5. **정밀 분석**: RE2 정규식 41개 + 토큰 분석기 1개(SQLI-010).
6. **점수 판정**: 필드별 점수 = 매칭 룰 가중치 합 + 신호 룰 가중치 − 예외. 요청 점수 = 필드 최댓값.
   BLOCK 모드 룰 합 ≥ 6 → 403, 전체 합 ≥ 6 → 전달 + 기록, 그 외 전달.
7. **이벤트**: DETECT_ONLY·BLOCK만 워커 메모리 deque에 넣고(await 없음) 백그라운드 태스크가 묶어서 XADD. admin-api 소비 그룹이 DB 커밋 후 XACK.

## 4. 데이터셋과 측정의 정직성

| 단계 | 공격 | 정상 | 탐지율 | 오탐률 |
|---|---:|---:|---:|---:|
| M1 1차본, 튜닝 전 | 569 | 320 | 93.50% | 1.88% |
| M1 1차본, 튜닝 후 | 569 | 320 | 100% | 0% |
| M1 직후, 튜닝에 안 쓴 기술 Q&A 40문장 | — | 40 | — | 차단 20% → 수정 후 10% |
| **M4 확장 셋, 튜닝 전** | 2,083 | 1,000 | **94.05%** | **1.70%** |
| M4 확장 셋, 튜닝 후(최종) | 2,081 | 1,000 | 100% | 0% |
| 최종 정책으로 어려운 기술 Q&A 40문장 | — | 40 | — | **차단 10% (4건)** |

- 확장 셋에서 튜닝 전 미탐은 **기본 페이로드 10여 개**에 몰려 있었다(변형별로 8~15개씩). 개별 페이로드가 아니라 **기법 단위**로 룰을 추가했다:
  괄호 서브쿼리(SQLI-017), CASE WHEN(SQLI-018), `IS NULL` 비교, 따옴표 없는 문맥의 문자열 tautology(SQLI-011 확장), 스킴 안 탭·개행 허용 `j\s*a\s*v\s*a…`(XSS-003),
  JS 문자열 탈출 `'-alert(1)-'`(XSS-015), `link rel=import`·`meta refresh`(XSS-013 확장), data URI 분리(XSS-007/016).
- 확장 셋의 튜닝 전 오탐 17건은 전부 `It's 'fine' -- don't worry` 였다. 토큰 분석기가 **닫는** 따옴표 뒤의 `--` 를 탈출로 본 것이 원인이라, 값 안에서 같은 종류 따옴표의 홀수 번째(여는 쪽)만 후보로 보도록 바꿨다.
- 남은 4건(`<script> 태그를…`, `<button onclick="save()">`, `Union SELECT 공격이…`, `A and 1=1`)은 문자열만으로 실제 페이로드와 구분할 수 없다. 이것이 시나리오 B가 다루는 경우이고, 경로·파라미터 단위 예외로 처리한다.
- 생성기가 만든 **무효 페이로드도 걸러냈다**: `&#x3cbody`(브라우저도 `&#x3cb` 까지 읽어 공격 불성립), 쿼리의 리터럴 `+`(공백이 됨), 폼·쿼리 값의 인코딩 안 된 `&`·`#`(값이 잘림).
  마지막 것은 실제 HTTP 재생(`tools/replay.py`)에서 오프라인 엔진과 54건 불일치로 드러났고, 백엔드 응답으로 공격이 전달되지 않음을 확인한 뒤 생성기를 고쳤다. 수정 후 **3,121건 전부 게이트웨이 판정 = 오프라인 엔진 판정**.

### 임계값 스윕 (쟁점 #1)

| 임계값 | 탐지율 | 차단율 | 오탐률(정상 1,000) | 차단 오탐(어려운 40) |
|---:|---:|---:|---:|---:|
| 4 | 100.00% | 99.95% | 0.20% | 27.5% |
| 5 | 100.00% | 99.71% | 0.00% | 12.5% |
| **6** | **100.00%** | **99.47%** | **0.00%** | **10.0%** |
| 7 | 86.83% | 85.58% | 0.00% | 5.0% |
| 8 | 82.56% | 80.97% | 0.00% | 0.0% |

6이 꺾이는 지점이다. 7로 올리면 탐지율이 13%p 떨어진다. 기술 Q&A 게시판처럼 공격 문법을 정상적으로 쓰는 경로의 오탐은 전역 임계값으로는 줄일 수 없으므로,
**경로별 임계값(쟁점 #1 ②안)을 다음 단계 필수 항목으로 권한다**(현재는 예외로 처리).

## 5. 부하·장애 측정 상세

**k6** (`loadtest/load.js`, 요청 구성: 상품 조회 70%, 검색 20%, 1 KB 게시글 작성 10%)

| 경로 | 요청 | 실패 | 평균 | p50 | p95 | p99 | 최대 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 백엔드 직접 (HTTP) | 54,001 | 0 | 0.57 ms | 0.54 ms | 0.86 ms | 1.10 ms | 9.0 ms |
| 게이트웨이 (HTTPS) | 180,001 | 0 | 2.34 ms | 2.08 ms | 3.58 ms | 6.75 ms | 91.9 ms |

- 게이트웨이 경로는 TLS 암호화 비용까지 포함하므로 보수적인 수치다. 게이트웨이 내부 히스토그램으로는 **검사 p99 ≤ 0.5 ms**, 앱 안 추가 지연 p95 ≤ 1 ms, p99 ≤ 3 ms였다.
  즉 추가 지연의 대부분은 탐지가 아니라 TLS·HTTP 파싱·프록시 홉이다.
- k6와 게이트웨이가 같은 호스트에서 CPU를 나눠 쓴 상태라, 실제 2 vCPU 전용 호스트에서는 조금 더 나을 것이다. 최대 91.9 ms는 측정 5분 시점의 정책 발행과 겹친 순간으로 보이나 원인은 특정하지 못했다.
- 기획서 쟁점 #4(“Python으로 300 RPS·p95 5 ms 가능한가”)는 **Uvicorn 워커 2개로 충족**했다. C 확장은 필요 없었다.

**장애 격리** (`tools/outage_drill.py`)

| 상황 | 결과 |
|---|---|
| admin-api + postgres 중단 | 공격 300건 판정이 엔진과 300/300 일치(차단 297, 탐지 3), 정상 300건 차단 0, 5xx 0 |
| redis 중단 | 공격 200건 판정 200/200 일치, 이벤트는 워커 버퍼에 보관, 유실 0 |
| 복구 후 | 두 단계에서 받은 요청 ID 500개 전부 `security_events` 에 존재 |
| DB 중단 상태에서 gateway 재시작 | 로컬 정책 캐시(v8)로 기동해 차단 유지, DB 복구 후 출처가 `db` 로 돌아옴 |

## 6. 개발 중 찾아 고친 결함

| 결함 | 영향 | 수정 |
|---|---|---|
| 시나리오 A가 SQLI-001과 SQLI-011에 중복 집계(16점) | 같은 증거를 두 번 세어 가중치 설계가 무의미 | SQLI-011을 따옴표 없는 문맥으로 한정 |
| 정규화기가 1 MB 입력에서 1.6초 | 목표의 30배 | google-re2 Python 바인딩의 `sub`가 매치마다 UTF-8↔str 오프셋을 변환. 고정 치환은 `str` 연산·선형 스캔으로 교체 |
| 회귀 거부 감사 기록이 사라짐 | 422 응답과 함께 트랜잭션이 롤백되어 `policy.publish_rejected` 미기록 | 거부 기록을 별도 트랜잭션으로 커밋 |
| `mpgctl create-admin --if-missing` 교착 | 커넥션을 쥔 채 `pool.close()` → init 컨테이너 무한 대기 | acquire 블록 밖에서 close |
| DB 복구 후에도 "리로드 실패" 알림 지속 | 같은 버전이면 오류를 지우기 전에 반환 | 조회 성공 시 오류 초기화 |
| 롤백 후 근거 없는 "미발행 변경" | 대상 버전에 없던 비활성 룰을 "추가"로 셈 | 비활성 + 발행본에 없음 → 변경 아님 |
| nginx HSTS 누락 | location의 `add_header` 가 server 블록 헤더 상속을 끊음 | location마다 지정 |

## 7. 보안 설계 요약

- 공격자에게는 `{"error":"blocked","request_id":…}` 만 준다(룰 ID·점수 비공개).
- 운영자 룰은 RE2만 허용(등록 시 컴파일 검사, 역참조·lookaround 거부). RE2는 Thompson NFA/DFA 기반이라 입력 길이에 선형이다(Russ Cox, *Regular Expression Matching Can Be Simple And Fast*, 2007).
- 예외는 룰 1개·경로·파라미터·만료일(≤ 180일) 필수, 와일드카드 금지(앱 검증 + DB CHECK 제약 이중), 회귀 게이트 통과 후에만 반영.
- 관리자: Argon2id, 5회 실패 15분 잠금 + IP당 10분 20회 제한, 세션은 Redis에 SHA-256 키로 저장(덤프로 세션 탈취 불가), 유휴 30분,
  쿠키 `HttpOnly; Secure; SameSite=Strict; Path=/admin/api`, 상태 변경 요청은 `X-CSRF-Token`, 역할 검사는 매 요청 DB에서 다시 확인.
- 콘솔은 모든 로그를 텍스트 노드로 렌더링(React 자동 이스케이프, `dangerouslySetInnerHTML` 미사용) + `script-src 'self'` CSP — 저장된 XSS 페이로드가 콘솔에서 실행되지 않는다.
- 로그에 남기지 않는 것: 요청 본문 원문, 쿠키 값, `password`·`token`·`secret` 류 파라미터 값. 샘플은 256자, 이메일·전화번호·긴 토큰 마스킹.
- 컨테이너: 비루트(uid 10001), 읽기 전용 루트 FS, `cap_drop: ALL`, `no-new-privileges`, 비밀값은 Docker secrets 파일.

## 8. 한계와 남은 일

- **문맥 의존 오탐**: 기술 Q&A 게시판 차단 오탐 10%(어려운 셋). 경로별 임계값 또는 경로별 룰 그룹이 필요하다.
- **퍼센트 이스케이프 폭주**: 1 MB 전체가 `%25` 반복이면 검사에 100~330 ms가 든다(`urllib.parse.unquote` 비용). 백엔드와 다르게 디코딩하면 그 차이가 우회 경로가 되므로 C 트릭으로 바꾸지 않았다. 이스케이프 밀도 상한을 정책으로 둘지 검토가 필요하다.
- **데이터셋**: 공격·정상 셋 모두 직접 만든 것이다. 실제 운영 트래픽 또는 공개 데이터셋(라이선스 확인 후)으로 다시 측정해야 일반화 성능을 말할 수 있다.
- **범위 밖**: 응답 검사, 명령어 삽입·경로 조작, 업로드 파일 내용, 다중 인스턴스, 내부망 TLS(기획서 9장 #7 — 다중 호스트로 나눌 때 PostgreSQL·Redis TLS 필수).
- **MVP JS 엔진과의 대조**: JS 원본이 없어 수행하지 못했다. 기획서의 시나리오 점수(A=10, B=11)를 정확히 재현하는 것으로 대신했다.
- 개발 환경 Python은 3.13(기획서 3.14.9), 데모 서버 실배포(공인 도메인 + Let's Encrypt)는 하지 않았다.
